# SM8650 v0.7：修复 v75 FP16 GroupNorm 累计格式，保留 CPU VAE

## 证据与范围

v0.6 的手机生成已正常：512×512、4 步，DiT 采样约 164.57 秒，CPU VAE 约 40 秒。RGB 三通道正常。CPU VAE 绕过此前异常的 HTP 解码路径，不能单凭这一点定位具体算子。

继续检查找到一个可独立复现的错误：`groupnorm-ops.c` 的 F16 输入分支使用 IEEE F32 累加；v75 的公共收尾函数却按 Hexagon qfloat 解释累计值。F32 输入分支本来使用 qfloat，因此之前的 FP8 矩阵检查和 F32 卷积检查不能覆盖这一错误。

直接使用生产代码在 `hexagon-sim -mv75` 运行，同一组 128 个数：

| 分支 | 均值 | 平方均值 |
| --- | --- | --- |
| CPU 参考 / 原 F32 分支 | 0.964844 | 1.30322 |
| 修复前 F16 分支 | 1.09051e-38 | 2.10252e-38 |

错误统计使方差接近零，归一化放大并破坏后续解码。AutoEncoderKL 的 direct-conv 解码会在上采样阶段切换至 F16 激活，随后 GroupNorm 因此触发此错误。它是已确认的内核缺陷，也是此前纯色的强嫌疑；尚未在手机上验证完整 DSP VAE，不能排除其他问题。

## 修改

- F16 输入复用 F32 输入的架构相关累计函数，保证累计与收尾的格式一致：v75 使用 qfloat；v79+ 使用 IEEE F32。
- **默认仍使用 CPU VAE**，关闭 direct-conv。DiT 与文本编码器仍使用 HTP；不提供自动切回 DSP 的行为。
- 手机适配诊断保留 16 组矩阵和 7 组卷积，新增独立进程的 **8 组 GroupNorm CPU 数值对照**，标记为 `HTP_NORM_DIAG`。覆盖 F16/F32、普通归一化、affine+SiLU、常量输入、9×9 尾部及 512×512×128 激活。
- 各 VAE 探测进程失败或超时后保留已有输出并继续其他探测，防止丢失前面的诊断。
- 保留 v0.6 的私有生成追踪与导出功能。无需重下模型。

## 验证

`tests/groupnorm_hvx_test.c` 包含实际生产实现，使用链接器移除未调用的 FastRPC/DMA 入口。v75 模拟器共 130 项：统计、非零均值、常量、小幅值、多个累计块、尾部毒值、affine/SiLU 输出及写入边界。修复后全部通过；旧实现同样的 130 项中有 86 项失败，F16 输出的归一化误差超过正常量级千倍。

运行方式（先执行 `build.sh`，从其编译数据库取得 SDK 路径）：

```sh
python3 app/src/main/cpp/dit/tests/run_groupnorm_hvx_test.py v75
```

模拟器测试覆盖数值计算，不覆盖 FastRPC、DMA 调度与完整模型。因此新增手机端对照，完整 DSP 出图仍待验证。

## 手机复测

1. 覆盖安装 v0.7。CPU 解码仍为默认，正常生成流程不变。
2. 退出生成页面，在设置中运行适配诊断，等待完成并保存日志。
3. 关注 `HTP_NORM_DIAG PASS` 和每组 `nrmse`，同时保留矩阵与卷积结果。大型检查最多允许每个进程运行 3 分钟。
4. 回传诊断后，再决定是否提供完整 DSP VAE 的独立对照试验。通过单算子自检不等于已验证完整解码。
